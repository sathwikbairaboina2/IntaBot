IntaBot — agentic Instagram management, self-hosted

Upload a picture; a worker writes the caption and picks the slot; you approve; a state machine publishes it. Comments come back through a webhook, get classified, and either get an auto-reply in the account voice or land on a human queue.

NestJS + Next.js API :4100 dashboard :3100 Swagger /docs BullMQ on Redis :6479 DynamoDB :8200 · MinIO :9200
What it is

A small number of Business accounts, run by machine, gated by a human

IntaBot manages Instagram Business accounts end to end: drafting posts, scheduling them, publishing through the Graph API, and moderating the comments that come back. It is built for a handful of accounts, self-hosted, with every model call replaceable by a deterministic fake.

The organising rule is that a model that cannot answer produces a work item, never a half-formed public reply. Every path where generation can fail ends on a human queue.

apps/api

NestJS. Cookie-session auth, accounts, media, approvals, moderation, the Instagram webhook, and five BullMQ workers in the same process.

apps/web

Next.js operator dashboard on :3100 — upload, approvals, moderation.

packages/shared

Zod schemas. PostStatus, CommentStatus, and the account shape are defined here and nowhere else.

Adapters, all swappable

instagram.port.ts and copy-writer.port.ts each have a fake and a real implementation. The whole loop runs offline.

Flow 1 of 4

Upload → draft → approve → publish

POST /media  (operator uploads a JPEG for an account)
   └─► draft queue
        └─ drafting.ts: copy writer writes a caption, slot-planner picks a time
             └─ Post { status: PENDING_APPROVAL }   ← appears on /approvals

operator ──► POST /approvals/:id/approve      (caption editable first)
                └─ Post { status: APPROVED }
                     └─► publish-scan queue (due posts) ──► publish queue
                          └─ create IG container ──► poll-container queue
                               └─ container ready ──► publish
                                    └─ Post { status: PUBLISHED, igMediaId, permalink }

operator ──► POST /approvals/:id/reject  →  Post { status: REJECTED }

Post states

DRAFT → PENDING_APPROVAL → APPROVED → PUBLISHING → PUBLISHED, with FAILED and REJECTED as terminal branches. Every post carries a version, so a stale approval from a second browser tab cannot overwrite a newer caption.

Dry run is the default

Accounts default to dryRun: true. Publishing then runs the full state machine — container creation, polling, the lot — and stops short of Instagram. Dry-run posts carry an igMediaId beginning dryrun-, so you can tell at a glance which side of the line a post is on. Real publishing needs the Meta setup, INSTAGRAM_MODE=live, and dryRun: false on the account.

Flow 2 of 4

A comment arrives and something happens to it

Instagram ──► POST /webhooks/instagram
                ├─ HMAC verified against META_APP_SECRET
                ├─ deduplicated
                └─ enqueued on the moderation queue

moderation.processor
   ├─ resolve the comment to a published post
   ├─ SELF-REPLY GUARD: the account's own comments are dropped BEFORE
   │    classification — the alternative is the bot talking to itself forever
   ├─ classify  { sentiment, intent, toxicity, isSpam, needsHuman }
   └─ policy gate
        ├─ account.moderationPaused        → classify, never reply
        ├─ blocklist term hit              → ESCALATED
        ├─ needsHuman                      → ESCALATED
        ├─ over replyCapPerPostPerHour
        │  or replyCapPerAccountPerHour    → ESCALATED
        ├─ isSpam                          → IGNORED
        └─ otherwise                       → AUTO_REPLIED in the account voice

Comment states: RECEIVED → AUTO_REPLIED | ESCALATED | IGNORED, and ESCALATED → HUMAN_REPLIED once an operator acts at /moderation with POST /moderation/:igCommentId/reply or POST /moderation/:igCommentId/dismiss.

Every decision — automatic or human — lands on the audit log with the rule that fired. Reply caps and the blocklist are per-account fields set through PATCH /accounts/:id: replyCapPerPostPerHour, replyCapPerAccountPerHour, blocklist.

Without Meta credentials the webhook route returns 503. The e2e suite signs its own webhooks with test secrets, so the whole loop still runs offline.

Flow 3 of 4

What happens when the model will not answer

LLM_PROVIDER picks what backs the copy writer, the comment classifier and the reply writer.

ValueBacked byNeeds
fakeDeterministic stubsnothing; the test default
anthropicclaude-opus-5ANTHROPIC_API_KEY
ollamaA local modelthe ollama service and one ollama pull

Leaving LLM_PROVIDER blank keeps the original rule: a present ANTHROPIC_API_KEY means Anthropic, no key means the fakes.

A local model has no equivalent of Anthropic's stop_reason: "refusal", so unusable output is the only signal it can give. OllamaClient retries once and then raises OllamaSchemaError, which each adapter maps onto the existing human-in-the-loop path:

  • copy writer → needsAttention on the post
  • classifier → needsHuman on the classification
  • reply writer → a reply-refused escalation

IntaBot runs its own Ollama container on :11437 rather than borrowing another project's: newer Qwen weights refuse to load on an older Ollama, and one stack's model upgrade must not be able to break another's.

Flow 4 of 4

Operator sign-in

  1. POST /auth/login { email, password }

    Argon2 verify. On success a session row is created and set as the intabot_session cookie — httpOnly, sameSite: lax, secure in production, expiring with the session (SESSION_TTL_HOURS).

  2. Every guarded route reads that cookie

    AuthGuard looks it up; there is no bearer token anywhere in this API.

  3. POST /auth/logout

    Revokes the session server-side and clears the cookie.

  4. GET /auth/me

    Returns the signed-in operator's email.

Operators are created from the CLI, which also creates the DynamoDB tables if they do not exist — so it is safe as the very first command against a fresh stack:

pnpm --filter @intabot/api run create-user you@example.com <password>

Instagram access tokens are encrypted at rest with TOKEN_ENCRYPTION_KEY (a base64 32-byte value you generate at setup).

Interface

API reference

Swagger UI is at http://localhost:4100/docs, with the raw document at /docs-json. It is wired in apps/api/src/main.ts and mounted only when NODE_ENV !== 'production' — the operator dashboard is the only intended client, and an unauthenticated route inventory is not worth publishing.

"Try it out" needs a browser session, not a token. Auth here is an httpOnly cookie, which Swagger UI cannot set. Run POST /auth/login first — from the docs page itself is fine — and the browser carries the cookie into every subsequent call. The document declares the cookie scheme as session for documentation purposes; there is nothing to paste into Authorize.
